# Требуемый серверный платёжный контракт для этапа 4

Проверены серверные `docs/client-api.md`, `docs/architecture.md` и исходный код
маршрутов. Платёжный backend, модели заказов и webhook сейчас отсутствуют.
Серверный проект не изменялся.

## Клиентские методы

Перед production-интеграцией потребуются типизированные методы:

1. `GET /api/v1/plans` — доступные тарифы и серверная цена. Клиент обязан
   проверять, что валюта и сумма соответствуют выбранному тарифу, но источником
   истины остаётся сервер.
2. `POST /api/v1/payment-orders` — создать заказ. Запрос содержит стабильный
   `plan_id` и `Idempotency-Key`; ответ — непрозрачный `order_id`, разрешённый
   HTTPS checkout URL, сумма, валюта, срок действия и начальный статус.
3. `GET /api/v1/payment-orders/{order_id}` — получить подтверждённое сервером
   состояние: `pending`, `paid`, `cancelled`, `failed` и актуальный объект
   подписки после `paid`.
4. Опциональный `POST /api/v1/payment-orders/{order_id}/cancel` — отменить
   незавершённый заказ, если это поддерживает провайдер.

Все методы должны быть привязаны к аутентифицированной клиентской сессии.
Клиент не должен передавать произвольную сумму, валюту или срок подписки.

## Webhook-процесс

Платёжный провайдер вызывает отдельный серверный endpoint. Обработчик обязан:

- проверять подпись по исходному телу запроса и секрету из защищённой
  конфигурации;
- проверять timestamp/nonce и ограничивать повторное воспроизведение;
- обеспечивать идемпотентность по provider event ID и transaction ID;
- находить только заранее созданный заказ;
- сверять сумму, валюту, тариф, merchant и provider account;
- менять подписку только после окончательного серверного статуса `paid`;
- обновлять заказ и подписку в одной транзакции с блокировкой от повторной
  обработки;
- безопасно учитывать отмену, истечение, возврат и chargeback;
- не помещать платёжные реквизиты, подписи и секрет webhook в аудит/логи;
- возвращать успешный ответ на уже обработанное событие без повторного
  продления подписки.

Переход клиента в `paid` допустим только после чтения подтверждённого состояния
с сервера. Переход `subscriptionUpdating` завершается повторным получением
актуальной подписки, а не локальным увеличением даты.

## Безопасность

- Только HTTPS и проверка сертификата.
- Checkout URL разрешается только для allowlist доменов провайдера.
- Нельзя считать редирект браузера доказательством оплаты.
- Нельзя доверять статусу, сумме или сроку из клиентского приложения.
- Ошибки для клиента не должны раскрывать webhook secret или внутренние ответы
  платёжного провайдера.
